# Razorpay Phase 5 review (pass 1)

## Evidence checked

- Guard and origin: all 12 handlers under `src/app/api/super-admin/billing/razorpay/` call `requireSuperAdmin(request)` first. Each POST (cancel, sync, webhook retry, reconcile) calls `isSameOrigin` straight after it, before the rate limit and any DB or Razorpay work. The ban POST now has the guard, then `isSameOrigin` (`@/lib/super-admin/request-origin`, which exists), then `isUuid`. The delete route already had the same-origin check.
- Re-auth before Razorpay: `cancel/route.ts` runs rate limit, then confirm, reason 5-500, then `verifySuperAdminReauth` (password, then 2FA). Only after that does it run `getSubscription` and `adminCancelSubscription`. `routes.test.ts:380-384` asserts `cancelSubscription`, `getSubscription` and rpc are not called on a wrong password. `reauth.ts` keeps the delete/verify messages and codes word for word. Sync takes no password, as the approved plan says (step 3).
- Delete refusal: `accounts/[id]/route.ts` runs token, then confirm word, then `assertDeletable`, then `cancelLiveAutopayForAccount`, then `deleteAccountRecords`. An `AutopayCancelError` or any other throw goes to the catch before `sa_delete_account`. `account-autopay.ts` checks reachability for every target before it cancels any, and treats only `isAlreadyInState || isNotFound` as acceptable. Tests: `delete-account.test.ts` checks the order `['cancelAutopay','rpc:sa_delete_account']`. It also checks that a 502 `autopay_cancel_failed` names `sub_Del000001` and that a 409 `autopay_unreachable` returns before `sa_delete_account`.
- Ban (D9): the server returns 409 `autopay_confirmation_required` with no ban when a cancellable AutoPay exists and `confirmAutopayCancel !== true`. `ban-route.test.ts:158` asserts `banAccount` is not called. With confirmation, the order is ban, then cancel. A failure keeps the account banned, reports `outcome:'failed'` and sends a `billing_anomaly` notification (`notifyAdmin` never throws, `store.ts:266`). The UI shows a second destructive confirm and resends with `confirmAutopayCancel:true`.
- No leaks: `admin-db.ts` lists every column explicitly. `WEBHOOK_LIST_COLUMNS` and `WEBHOOK_DETAIL_COLUMNS` leave out `payload`, and nothing selects `*`. `routes.test.ts:307-331` checks the recorded select strings. Subscription and payment projections carry no tokens or secrets. Payments expose only `vpa_masked`.
- Migration: additive and idempotent. It drops and re-adds the CHECK with all 24 previous values plus `billing_admin_action`. It adds columns with `ADD COLUMN IF NOT EXISTS`. All three functions are `SECURITY DEFINER` with `SET search_path = public`, and each has `REVOKE ALL ... FROM PUBLIC, anon, authenticated` plus `GRANT EXECUTE ... TO service_role` on its exact signature. The requeue runs as one conditional `UPDATE ... WHERE status IN ('failed','dead')`. `verification.md` records live md5 matches for the function bodies and an unchanged demo account md5 and table counts.
- Copy: none of the added lines in modified UI files contain em dashes or exclamation marks (diff scan). The new files use `—` only as a placeholder glyph for empty values in table cells. That follows the existing panel convention and is not prose. New prose strings (ban confirm, toasts, delete note, refusal messages) are plain.
- Test-mode labels: `ModeBadge` is rendered on every test row in the subscriptions, transactions, invoices, refunds, disputes and webhooks panels, the drawer title, the overview per-mode header, the reconciliation runs table and the Subscribers AutoPay cell.
- Tests assert real columns. `account-autopay.test.ts` asserts the table, the exact column list, `eq('account_id', ACCOUNT_ID)` and the `in('status', [...])` values. `routes.test.ts` asserts rpc names with `p_actor` and the select strings. `ban-route.test.ts` asserts the `banAccount(ACCT,'Spam','admin-1')` arguments.
