## Design decisions (made by the planner, grounded in the code read)

1. **One migration is needed**: `supabase/migrations/20261024000000_razorpay_billing_phase5.sql` (the newest existing file is `20261023010000_razorpay_billing_method_summary.sql`). Reasons:
   - `subscription_events.account_id` is NOT NULL and `event_type` has a CHECK, so an admin audit row ("synced", "re-queued", "cancelled by admin with reason X") needs a new event type. The snapshot apply (`billing_apply_subscription_snapshot`) already writes `autopay_cancelled` with `source=p_source` but no actor or reason, so we write a separate `billing_admin_action` event carrying `actor_user_id` and the typed reason. `listCustomerPlanActivity` in `src/lib/subscription/queries.ts` uses an allowlist (`CUSTOMER_VISIBLE_EVENTS`), so the new type stays hidden from customers automatically.
   - `billing_claim_webhook_events` never re-claims `dead` rows and `processDueWebhookEvents` marks dead at `attempts >= 6`, so a retry must reset `status`/`attempts` atomically, and only from `failed`/`dead`. A SQL function does that in one statement and records who did it.
   - Webhook retries and reconciliation runs are not always account-scoped, so they are audited on their own rows (`billing_webhook_events.requeued_by/requeued_at/requeue_count`, `billing_reconciliation_runs.triggered_by`) plus a `billing_admin_action` event whenever an account is known.
   - Overview counts (status x mode, upcoming charges, failures, webhook health, last run) are one STABLE SQL function instead of ~30 count queries.
   - The super-admin notification CHECK already has the billing types (`autopay_halted`, `billing_dispute`, `billing_webhook_dead`, `billing_anomaly`, `billing_refund`, migration `20261022000000`), so the plan's "migration for the notification CHECK" is already done. No change there.
2. **Admin cancel is always immediate** (`cancelSubscription(pid, false)`), not "immediate or at cycle end". Same reasoning as Phase 4 `lifecycle.ts`: access lives in `accounts.subscription_ends_at`, which a cancel never touches, so the customer keeps paid time either way, and "at cycle end" on a pending/halted mandate could still collect. Recorded as a deviation from §7.4.
3. **Admin cancel re-auth is one step** (password + 2FA code in the same POST as reason and confirm), not the delete flow's token handshake, because there is only one call. The password/2FA logic is extracted from `delete/verify/route.ts` into a shared helper so both use identical checks and messages.
4. **Mode safety**: lists show both modes from the shared DB, with a mode filter and an amber "Test" pill on every test row. Any action that calls Razorpay (sync, cancel, webhook retry, delete/ban cancel) requires `row.mode === readRazorpayConfig().mode`; otherwise 409 `mode_unavailable`. Production (Razorpay not configured) therefore refuses to delete or ban-cancel an account whose AutoPay it cannot reach, instead of silently orphaning a mandate.
5. **Live statuses for delete/ban** (brief + F7): `created, authenticated, active, pending, halted, paused` = `LIVE_AUTOPAY_STATUSES`. A fresh `initiating` claim (< 15 min old, no provider id yet) blocks delete because a Razorpay subscription may be created a second later; older `initiating`/`failed_to_create` rows have nothing to cancel and are ignored. **Charging statuses for F6**: `authenticated, active, pending` (same as `view.ts` `WORKING`), because only those will be charged on `charge_at`.
6. **Tolerated Razorpay errors**: `RazorpayApiError.isAlreadyInState || isNotFound` (same as `lifecycle.ts`, `reconcile.ts`). Anything else refuses the delete.
7. **Delete order (D9)**: all existing checks, then cancel every live AutoPay, then `sa_delete_account` (billing rows cascade with the account; Razorpay keeps its records), then storage purge. If any cancel fails, nothing is deleted.
8. **Ban order (D9)**: ban is a safety action and must never be blocked by a Razorpay outage. Server-enforced confirmation: if a live AutoPay exists and the body lacks `confirmAutopayCancel: true`, answer 409 `autopay_confirmation_required` without banning. With confirmation: `banAccount` first, then cancel AutoPay, then report `autopay.outcome` (`none` | `cancelled` | `failed`). A failure raises a `billing_anomaly` super-admin notification. Unban does not restore AutoPay. The ban POST also gets `isSameOrigin` (it now changes billing).
9. **Customer email on admin cancel**: the snapshot apply enqueues the normal `autopay_cancelled` email; we keep it (it is true) and deliver it from `after()` for the cancel route and ban. On delete the outbox rows cascade away, so no email is sent to a deleted workspace.
10. **Default tab is `overview`**, tab order follows §9. The old "Payment requests" tab becomes "Manual payments" with the same panel and drawer (approve/reject is already offered only for `pending` rows, `payment-request-drawer.tsx` `isPending`). Production still runs `manual_upi`, so it stays fully working; Phase 6 retires it. The pending count stays on the tab label.
11. **Tab state in the URL** (`?tab=…&sub=<billing_subscription_id>`) via `useSearchParams` + `replaceSearchParams` under a `Suspense` boundary, the pattern in `src/app/(dashboard)/settings/page.tsx`.
12. **Razorpay Dashboard deep links**: `https://dashboard.razorpay.com/app/subscriptions/{sub_id}` and `/app/payments/{pay_id}`. The URL format is an assumption; label it "Open in Razorpay" and note it as unverified in the report if it cannot be confirmed.

## Shapes used below

- List response: `{ items: T[], total: number, page: number, pageSize: number, totalPages: number }`, header `Cache-Control: no-store`.
- List query params (validated by allowlist in `admin-query.ts`, unknown values fall back to defaults, never passed raw into `.order()`): `mode=all|test|live` (default all), `status`, `method`, `search`, `sort`, `dir=asc|desc` (default desc), `page>=1` (default 1), `pageSize∈{10,20,50,100}` (default 20).
- `search`: if it matches `^(sub|pay|inv|rfnd|disp|plan|cust)_[A-Za-z0-9]+$` it is an exact provider-id match on the relevant column; otherwise accounts are looked up by `name ilike %search%` (escape `\ % _ ,`, limit 200) and the list is filtered with `.in('account_id', ids)` (empty → empty page).
- Every row carries `mode` and `accountName` (one `accounts(id,name)` lookup for the page's ids).
- Error shape: `{ error: string, code: string }` with status; Razorpay errors go through `toRazorpayErrorResponse` (502 `provider_error`, 503 `billing_unavailable`).

## Spec ambiguities and decisions

- §7.4 "immediate or at cycle end": immediate only (decision 2).
- §9 "Manual payments read-only": kept actionable for `pending` rows only, because production is still `manual_upi` (decision 10).
- §15 "migration for the notification CHECK": already in Phase 3; the new migration covers audit, requeue and overview instead (decision 1).
- "Audited" for sync/retry/reconcile has no named sink: `subscription_events` (`billing_admin_action`, `source='admin'`, `actor_user_id`) when an account is known, plus the row-level columns for webhook events and reconciliation runs.
- Ban "after confirmation": confirmation is enforced by the server (409 handshake), not just the UI dialog (decision 8).
- Acceptance "25+ seeded demo-mode rows": done as part of the rolled-back SQL block in step 1 if the coder seeds rows there; otherwise covered by unit tests and listed as open.
